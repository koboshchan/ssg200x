TableTalk currently uses Clerk account IDs as v1 cryptographic identities. Hashing the display label does not sanitize the wire.

The state response exposes all currently approved, non-revoked members' IDs through members[].userId and, while present, owner.userId. Device IDs, public signing keys, public ECDH keys and their fingerprints are also exposed to authorized room peers. The latter public keys are necessary for the existing peer encryption and verification design, not private keys.

Each returned key wrap includes its original senderUserId and toUserId. The recipient is the authenticated account, but the sender may be a former member or an old account-key incarnation. State pagination returns grants only for the caller's current account-key device IDs. Historical grants can therefore expose a former grantor's ID even when that grantor is no longer in the current directory.

Each returned history message and successful send acknowledgement includes the original senderUserId. History requires a grant for the authenticated account and requested device. Wrap acknowledgements also return their original sender and recipient IDs. Requests to grant a key name the recipient in toUserId. No separate raw sender ID is supplied by the sending client, since the service derives it from the authenticated account.

In runtime/chat-protocol.mjs, messageHeader binds the original sender ID into the signature and AES-GCM additional authenticated data. wrapHeader binds both original sender and recipient IDs into the signature, HKDF info and AES-GCM additional authenticated data. Replacing DTO fields invalidates those bindings. Even a new signature from the real sender cannot repair the existing encryption bindings. The server does not hold the private keys or plaintext necessary to reseal history.

Account registration, account-key publication signatures and the encrypted recovery backup also bind the account ID. These own-account uses are distinct from exposing another account's ID to room peers. A future public-ID wire protocol must preserve authenticated server-side account ownership and the original recovery-backup binding instead of globally replacing every ID.

A reviewed v2 could use the existing room member publicId for new peer-facing identities while preserving v1 reads exactly. It would need explicit versioned signature/AAD/HKDF domains, server-side ownership resolution, stable legacy device trust and pending-send compatibility, and recovery/history regression tests. This has not been implemented. The test showing that the existing keypairs can create public-ID-bound ciphertext is only a feasibility check, not a complete v2 protocol or migration.

A v2 with unchanged v1 read compatibility still exposes the original Clerk IDs whenever a legacy wrap or message is read. It can prevent new legacy bindings, but cannot truthfully promise a Clerk-ID-free history response. Removing IDs from the current directory would be a prospective improvement, not a complete historical privacy migration.

A fresh browser restores its account private keys with recovery words but has no preexisting peer ID map. An encrypted legacy binding map could change where those IDs are transported, but authorized clients would still learn the original identities after decrypting the map. Client-assisted re-encryption would need a separate reviewed design, participating key holders and explicit decisions about preservation of original sender authenticity. No such migration is approved here.

An approved reset could abandon legacy history, but that would break the current preservation requirement and would not retract IDs already seen by peers. No reset, deletion, hidden history, runtime change or deployment is part of this audit.

The regression tests in tests/chat-identity-boundary.test.ts execute real WebCrypto to prove the legacy remapping failure and prospective public-ID encryption with the same account keypairs. They also exercise the actual service's nonmember rejection before any directory/history/backup read with a minimal collection adapter, and the actual account-publication validator's rejection of another account's signed payload before persistence reads. These are not Mongo integration, live Clerk authentication or production socket tests. Socket session validation belongs to the separate authentication audit.
